# Требования к серверу для авторизации

Этот документ разделяет требования главы 9 технического задания на решения, которые можно реализовать по общепринятой практике, решения, которые нужно согласовать, и данные, которые должен предоставить сервер.

## 1. Можно реализовать по общепринятой практике

Эти решения не требуют уникальных данных от владельца сервера:

- Kotlin + Jetpack Compose для экранов;
- `ViewModel` для состояния форм;
- `Repository` между UI и API;
- Retrofit/OkHttp или аналогичный HTTP-клиент;
- заголовок `Authorization: Bearer <accessToken>`;
- хранение токенов через Android Keystore;
- отсутствие хранения пароля на устройстве;
- локальная проверка пустых полей;
- проверка совпадения пароля и подтверждения;
- маскирование поля пароля;
- блокировка кнопки во время запроса;
- состояния `Loading`, `Success` и `Error`;
- автоматическое обновление access token после `401`;
- удаление локальной сессии при недействительном refresh token;
- открытие главной страницы после успешной авторизации;
- открытие Login при отсутствии действительной сессии;
- сохранение пользователя в Room;
- сохранение состояния входа между перезапусками;
- очистка токенов при logout;
- понятные сообщения вместо `HTTP 401` или `HTTP 500`.

Подтверждение пароля обычно отправляется только на серверную проверку формы не нужно. Клиент передает `login`, `password` и, при необходимости, `email`.

## 2. Нужно согласовать, но можно выбрать стандартный вариант

Здесь существует несколько допустимых решений, но необходимо выбрать и зафиксировать одно:

- JWT или opaque access token;
- срок жизни access token;
- срок жизни refresh token;
- ротация refresh token;
- автоматический вход после регистрации или повторный вход;
- необходимость подтверждения email;
- возможность входа с нескольких устройств;
- отзыв одной сессии или всех сессий при logout;
- обязательность email;
- правила логина и пароля;
- лимит попыток входа;
- формат даты и времени;
- язык сообщений об ошибках.

Если сервер уже существует, Android-клиент должен подстроиться под его фактическое поведение.

## 3. Уникальные данные, которые должен предоставить сервер

Без этих данных корректная интеграция невозможна.

### 3.1. Адрес API

Например:

```text
https://api.example.com/
```

### 3.2. Реальные маршруты

Техническое задание предлагает следующие маршруты:

```text
POST /auth/register
POST /auth/login
POST /auth/refresh
POST /auth/logout
```

Но фактические URL определяет сервер. Например, он может использовать:

```text
POST /api/v1/users
POST /api/v1/auth/sign-in
POST /api/v1/auth/refresh-token
```

Для Android важны реальные адреса и HTTP-методы.

### 3.3. Формат запросов

Например, сервер может ожидать:

```json
{
  "login": "ivan",
  "password": "secret"
}
```

или:

```json
{
  "username": "ivan",
  "password": "secret",
  "email": "ivan@example.com"
}
```

Названия полей нельзя надежно определить без серверного контракта.

### 3.4. Формат успешных ответов

Нужно знать, возвращает ли сервер:

- пользователя;
- access token;
- refresh token;
- срок действия токена;
- идентификатор семьи;
- роль пользователя.

Например:

```json
{
  "accessToken": "...",
  "refreshToken": "...",
  "expiresIn": 900,
  "user": {
    "id": "uuid",
    "login": "ivan"
  }
}
```

### 3.5. Формат ошибок

Например:

```json
{
  "code": "INVALID_CREDENTIALS",
  "message": "Invalid login or password"
}
```

Важно знать, как сервер обозначает:

- неправильный пароль;
- занятый логин;
- истекший refresh token;
- заблокированный аккаунт;
- ошибку валидации;
- превышение числа попыток.

### 3.6. Механизм refresh

Нужно точно знать:

- передается ли refresh token в JSON;
- возвращается ли новый refresh token;
- можно ли использовать старый refresh token после обновления;
- какой ответ приходит при отзыве токена.

### 3.7. Получение текущего пользователя

Для восстановления сессии желательно иметь:

```text
GET /auth/me
```

или аналогичный маршрут.

Он нужен после перезапуска приложения, чтобы проверить сохраненную сессию и получить актуальные данные пользователя.

### 3.8. Logout

Нужно знать:

- требует ли logout access token;
- передается ли refresh token;
- удаляет ли сервер одну сессию;
- отзывает ли сервер все сессии пользователя.

### 3.9. HTTPS и сертификат

Для production нужен настоящий HTTPS. Если тестовый сервер использует самоподписанный сертификат, потребуется отдельная настройка. Отключать стандартную проверку сертификата в production нельзя.

## 4. Что нужно предоставить владельцу проекта

Минимальный обязательный набор:

```text
Base URL API
Реальные auth-маршруты
JSON регистрации
JSON входа
JSON refresh
JSON logout
JSON ошибок
Срок жизни токенов
Правила ротации refresh token
Наличие /auth/me
Требуется ли подтверждение email
Правила логина и пароля
```

Предпочтительный способ передачи этого набора — Swagger/OpenAPI или документация API.

Для разработки также понадобятся тестовый URL и тестовый аккаунт либо инструкция его создания.

## 5. Что предоставлять не нужно

Не нужно передавать:

- production-пароли;
- реальные refresh token;
- приватные ключи;
- секреты подписи JWT;
- доступ к базе данных.

Для разработки достаточно тестовых данных и документации API.

## 6. Итог

Архитектуру Android-клиента можно реализовать по стандартной практике. Но следующие сведения должны точно соответствовать серверу:

- адреса и методы API;
- имена полей JSON;
- структура успешных ответов;
- структура ошибок;
- правила access/refresh token;
- поведение logout;
- способ получения текущего пользователя.

Особенно важны `GET /auth/me`, точные JSON-ответы и правила работы refresh token. Без них можно сделать только демонстрационную авторизацию, но нельзя надежно восстановить сессию после перезапуска и истечения access token.

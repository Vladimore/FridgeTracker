
# Техническое задание v2.0

## Приложение для учёта продуктов в холодильнике

**Версия:** 2.0
**Тип:** Android-приложение
**Основной режим:** offline-first с последующей синхронизацией с сервером
**UI:** Kotlin + Jetpack Compose + Material 3
**Локальная БД:** Room
**Локальные настройки:** DataStore
**Удалённый сервер:** REST API
**Основной принцип:** локальные данные доступны без интернета, сервер используется для синхронизации, семейного доступа, штрихкодов и общей аналитики.

---

# 1. Цель приложения

Приложение предназначено для ведения общего списка продуктов пользователя или семьи.

Основные возможности:

* добавление продуктов;
* редактирование;
* удаление;
* контроль текущего остатка;
* уменьшение остатка одним нажатием;
* категории;
* пользовательские дополнительные поля;
* сроки годности;
* поиск;
* добавление по штрихкоду;
* локальный кэш данных штрихкодов;
* синхронизация между устройствами;
* семейный аккаунт;
* история действий;
* статистика использования продуктов;
* список покупок;
* уведомления;
* рекомендации;
* передача списков другим приложениям.

---

# 2. Основные принципы архитектуры

Приложение должно проектироваться не как полностью локальное приложение с последующим «прикручиванием» сервера, а сразу с учётом будущей синхронизации.

Основной принцип:

```text
UI
 ↓
ViewModel
 ↓
Use Case / Repository
 ↓
Local Database
 ↓
Sync Queue
 ↓
Remote API
```

UI не должен напрямую обращаться:

* к Room;
* к HTTP API;
* к файловой системе;
* к системным сервисам.

---

# 3. Offline-first

Приложение должно работать без интернета.

Без подключения к серверу пользователь должен иметь возможность:

* просматривать продукты;
* искать продукты;
* добавлять продукты;
* редактировать продукты;
* удалять продукты;
* уменьшать остаток;
* работать с категориями;
* работать с корзиной;
* изменять локальные настройки;
* просматривать локальную историю;
* использовать ранее сохранённые данные штрихкодов.

При восстановлении интернет-соединения приложение автоматически синхронизирует накопившиеся изменения с сервером.

# 5. Семейный аккаунт

Главная сущность совместной работы — **семья**, а не отдельный пользователь.

Пример:

```text
Семья
 ├── Владелец
 ├── Пользователь 1
 └── Пользователь 2
```

Продукты принадлежат семье.

Поэтому все участники видят единую картотеку продуктов.

Например:

```text
Иван добавил молоко
        ↓
Молоко появляется
у Ивана, Анны и Петра
```

---

# 6. Роли семейного аккаунта

Использовать:

```text
OWNER
MEMBER
```

`OWNER`:

* управляет семьёй;
* приглашает участников;
* принимает заявки;
* удаляет участников;
* видит всех участников.

`MEMBER`:

* работает с продуктами;
* работает с корзиной;
* видит историю и аналитику;
* изменяет собственные настройки.

---

# 7. Приглашение пользователей

Не использовать общий пароль владельца.

Использовать **код приглашения в семью**.

Процесс:

```text
Владелец
 ↓
Создать приглашение
 ↓
Код приглашения
 ↓
Новый пользователь
 ↓
Вводит код
 ↓
Создаёт собственный аккаунт
 ↓
Заявка
 ↓
Владелец подтверждает
 ↓
Пользователь становится MEMBER
```

Код приглашения должен:

* генерироваться сервером;
* быть случайным;
* не совпадать с паролем;
* не давать доступа к аккаунту владельца;
* иметь возможность отзыва;
* желательно иметь срок действия.

# 16. Product

Основная сущность продукта:

```text
Product
----------------
id: UUID
familyId: UUID
name: String
imageUri: String?

categoryId: UUID?

updatedAt: DateTime

```

### Важное правило

`initialQuantity` и `currentQuantity` должны храниться отдельно.

Пример:

```text
initialQuantity = 1.0
currentQuantity = 0.9
```

Это позволяет вычислять:

```text
90%
```

---

# 17. Вес

Вес и количество — разные параметры.

Например:

```text
Название: Молоко
Вес: 1
Единица веса: л
Количество: 2
```

В интерфейсе это может отображаться как:

> 2 × 1 л

На первом этапе можно использовать:

* кг;
* г;
* л;
* мл;
* шт.

Архитектура должна позволять добавить другие единицы.

---

# 18. Остаток

При создании:

```text
currentQuantity = initialQuantity
```

При нажатии `-`:

```text
currentQuantity =
max(0, currentQuantity - decrementStep)
```

Если `decrementStep` не установлен:

```text
decrementStep = 1
```

---

# 19. Процент остатка

Рассчитывается:

```text
currentQuantity / initialQuantity × 100
```

Например:

```text
Изначально: 1
Текущее: 0.9

Остаток: 0.9 (90%)
```

Если первоначальное количество равно 0, процент не рассчитывается.

---

# 20. Поведение законченного продукта

Когда:

```text
currentQuantity = 0
```

продукт не удаляется автоматически.

Это важно для:

* истории;
* аналитики;
* повторной покупки;
* статистики.

Карточка может визуально исчезнуть из основного списка с анимацией, если это предусмотрено выбранной логикой отображения.

Сам продукт остаётся в БД.

# 38. Важное архитектурное правило для добавления

Добавление должно сначала записывать данные в локальную БД.

После этого создаётся операция синхронизации:

```text
SyncOperation
```

Если интернета нет, операция остаётся в очереди.

Если интернет есть — отправляется на сервер.

Таким образом, добавление продукта не зависит от доступности сервера.

# 52. Сохранение

* данные сохраняются;
* создаётся `ProductAction = UPDATED`;
* создаётся SyncOperation;
* окно закрывается;
* пользователь остаётся на Главной.

# 53. Удаление

При нажатии:

> Удалить карточку?

Кнопки:

**Да**

**Нет**

`Нет`:

* закрывает подтверждение;
* оставляет редактирование открытым.

`Да`:

* продукт помечается удалённым;
* создаётся история;
* создаётся SyncOperation;
* окна закрываются.

Физическое удаление выполняется сервером/клиентом только после безопасной синхронизации и при необходимости очистки.

# 78. Предупреждения

Два состояния:

### Скоро закончится срок


### Просрочен

```text
expirationDate < currentDate
```

`warningPeriod` должен быть настраиваемым.

Например:

* 1 день;
* 3 дня;
* 7 дней.


В дальнейшем можно добавить более сложную стратегию объединения.

Повторная отправка одной операции не должна приводить к двойному добавлению продукта.

Для этого операции должны иметь уникальный:

```text
operationId
```

Сервер запоминает обработанные операции.

# 114. Критерии готовности

Функция считается реализованной только если:

1. Она работает после перезапуска приложения.
2. Она не ломается без интернета, если относится к offline-функциям.
3. Она корректно синхронизируется после появления интернета.
4. Ошибки обрабатываются.
5. Состояние UI корректно после поворота/пересоздания Activity.
6. Настройки сохраняются.
7. Данные не теряются.
8. Есть соответствующая запись истории, если действие должно попасть в историю.

* использовать пароль владельца как код приглашения;
* отправлять каждый запрос напрямую из UI;
* требовать интернет для обычной работы;
* удалять продукт физически сразу после окончания остатка;
* хранить серверные ID только как `Long`;
* жёстко зашивать список будущих дополнительных полей;
* делать прямую обязательную интеграцию только с Telegram/VK.

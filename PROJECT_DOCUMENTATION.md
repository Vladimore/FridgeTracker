# Документация проекта

## Назначение

Fridge Tracker хранит продукты локально и проектируется так, чтобы серверная синхронизация подключалась через интерфейс, а не из Compose-кода. Пока сервер недоступен, данные не должны теряться и приложение должно продолжать работать.

## Реализовано в текущем срезе

- Compose-приложение с одной Activity и Navigation Compose.
- Room database v2 с UUID-идентификаторами.
- `Product`: семья, дата добавления, изображение URI, категория, штрихкод, вес, начальное и текущее количество, срок годности, шаг уменьшения, серверная версия и soft delete.
- Локальные сущности для `User`, `Family`, `FamilyMember`, `Category`, динамических полей, barcode cache, shopping list, product history и sync queue.
- Репозиторий записывает продукт и добавляет операцию синхронизации. Уменьшение количества не удаляет продукт при нулевом остатке.
- Поиск выполняется Room-запросом для отдельной строки поиска; текущий экран также сохраняет быстрый UI-фильтр уже загруженного списка.
- DataStore сохраняет тему и состояние уведомлений между перезапусками.
- `SyncWorker` определяет место для retry/backoff без требования сети.

## Заглушки сервера

Все удалённые вызовы находятся за `RemoteApi`. Текущая реализация `RemoteApiStub` возвращает `NotConfigured`. Таблица URL и точек замены: [REMOTE_API_STUBS.md](REMOTE_API_STUBS.md).

При подключении сервера нужно добавить настоящую реализацию `RemoteApi`, HTTPS-клиент, безопасное хранилище access/refresh token, обработку HTTP-ошибок, idempotency по `SyncOperationEntity.id`, optimistic locking по `serverVersion` и worker с сетевым constraint.

## Что ещё требует отдельного UI-среза

Модель уже подготовлена, но полноценной пользовательской реализации требуют: регистрация/login, семейные приглашения и роли, экран категорий с динамическими полями, CameraX barcode scanner, полноценная корзина и Sharesheet, вкладки истории/аналитики, уведомления WorkManager и двухколоночный режим. Эти части не имитируются фиктивными сетевыми ответами: вместо этого оставлены локальные сущности и безопасные точки расширения.

## Проверка

Основная проверка проекта:

```text
gradlew.bat :app:compileDebugKotlin --no-daemon
gradlew.bat :app:assembleDebug --no-daemon
```

При первом запуске после перехода со старого прототипа база пересоздаётся через `fallbackToDestructiveMigration()`. Для production необходимо заменить это на явную миграцию с сохранением старых данных.

## Правила дальнейшей разработки

1. UI не обращается к Room, HTTP или файловой системе напрямую.
2. Изменение продукта сначала фиксируется локально, затем попадает в sync queue.
3. Пароли не хранятся локально.
4. Продукты с нулевым остатком не удаляются физически.
5. Реальные URL и авторизация не добавляются в Compose-экраны.
